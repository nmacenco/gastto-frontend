# Internationalization Contract: Spanish-First Landing Page

## Release Behavior

- The default and only enabled locale is Spanish with the BCP 47 tag `es`.
- `/` renders Spanish and declares `<html lang="es">`.
- The release has no language selector, locale cookie, browser-language negotiation, or
  locale-prefixed route.
- Every user-visible string, including metadata, accessible labels, and informative alternative
  text, MUST be resolved through `next-intl`.

## File Ownership

```text
messages/
└── es.json              # Source catalog and message-key schema

src/i18n/
├── config.ts            # defaultLocale, supportedLocales, locale labels and Locale type
└── request.ts           # next-intl request configuration and catalog loader

global.ts                # next-intl AppConfig type augmentation
```

`src/config/site.ts` contains language-neutral public configuration only. Components and site
configuration MUST NOT duplicate translated copy. Root-level `global.ts` owns the `next-intl`
`AppConfig` augmentation for the locale and message types.

## Catalog Shape

Top-level namespaces MUST be `Metadata`, `Header`, `Hero`, `HowItWorks`, `Benefits`, `Reassurance`,
`FinalCta`, and `Footer`. Keys use stable descriptive English identifiers; values use the catalog's
language. Keys MUST describe meaning rather than repeat source wording.

Use ICU arguments for variable text and pluralization. Argument names are part of the contract and
MUST remain identical across catalogs. Do not assemble sentences by concatenating separately
translated fragments.

## Type and Validation Rules

- TypeScript message augmentation MUST derive valid namespaces and keys from `messages/es.json`.
- The locale registry MUST use a readonly literal list so `Locale` is inferred from its members.
- The `next-intl` plugin MUST generate exact message declarations from `messages/es.json` so ICU
  arguments are type checked; `messages/*.d.json.ts` MUST be ignored by Git.
- Every registered locale MUST have exactly the source catalog's keys and compatible ICU argument
  names.
- Missing catalogs, missing or extra keys, malformed ICU messages, and unsupported registered locale
  tags MUST fail an automated quality gate before production build completion.
- Tests MUST prove that Spanish messages render, metadata is localized, and the root document uses
  `lang="es"`.

## Adding a Language

1. Copy `messages/es.json` to `messages/{bcp47-tag}.json`.
2. Translate values while retaining keys, markup placeholders, and ICU argument names.
3. Add the tag and its endonym to `src/i18n/config.ts`.
4. Run catalog validation, type checking, component tests, and the production build.

No landing-page component or layout edit is allowed solely to add the catalog. Making the language
publicly selectable requires a follow-up decision for localized URLs, negotiation, SEO alternates,
and the selector UX; those behaviors are intentionally outside this release.
